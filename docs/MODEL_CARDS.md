# Model Cards

All metrics below are pulled directly from `ml/artifacts/summary.json`, generated by `python -m ml.pipeline.train_all`, and have been independently re-run and cross-checked during development. No estimated or placeholder values are included.

---

## 1. XGBoost RUL Regression (CMAPSS FD001)

**Task:** predict Remaining Useful Life (RUL), in cycles, for turbofan engines using the NASA CMAPSS FD001 dataset.

**Features (107 total):**
- Raw sensor readings (15 of the original 21 sensors — 6 low-variance sensors were dropped during feature selection)
- Two operational settings
- Rolling 5-cycle mean and std per sensor
- Rolling 20-cycle mean and std per sensor
- Baseline deviation (current value minus the engine's own early-life mean)
- 20-cycle trend (first-to-last delta within the rolling window)
- All features MinMax-scaled to [0, 1] (`ml/artifacts/regression/cmapss_scaler.joblib`)

**Target:** RUL clipped at 125 cycles (piecewise: constant during early healthy life, linearly decreasing near end-of-life), matching the correctly-decreasing per-cycle value for both train and test.

**Performance (official FD001 test set):**
| Metric | Value |
|---|---|
| RMSE | 12.25 cycles |
| MAE | 8.48 cycles |
| R² | 0.80 |

For reference, a published baseline on this exact dataset tier using only raw sensors (Koen Peters, Towards Data Science, "Random Forest for predictive maintenance of turbofan engines") reports RMSE ~20–22, R² ~0.71–0.75. This model's engineered features improve meaningfully on that baseline.

**Why XGBoost:** tabular gradient boosting is a strong, fast, interpretable baseline for this feature set, and outperformed the from-scratch LSTM (below) on this task.

## 2. LSTM RUL Regression (CMAPSS FD001)

**Architecture:** single-layer LSTM, 32 hidden units, sequence length 30 cycles, fully-connected output head. Adam optimizer, learning rate 0.01, batch size 256, 60 epochs.

**Reproducibility:** `torch.manual_seed()` alone was found insufficient to make training deterministic — the same seed produced different R² values across runs (0.78, 0.66, -0.64, -0.25) with identical code and data. `torch.use_deterministic_algorithms(True)` was required in addition to close this gap; verified bit-identical output across repeated runs after the fix.

**Performance (official FD001 test set):**
| Metric | Value |
|---|---|
| RMSE | 14.37 cycles |
| MAE | 9.36 cycles |
| R² | 0.77 |

**Debugging note — target/input scale mismatch:** the initial implementation trained on inputs MinMax-scaled to [0, 1] but left the RUL target unscaled (range 0–125). This mismatch caused the model to collapse into predicting close to the constant mean RUL for every input, rather than learning from the sensor sequences — confirmed by the training loss flatlining at ~1747, almost exactly the variance of the unscaled target (1736.6). Scaling the target to [0, 1] during training and rescaling predictions back to real units at evaluation time fixed this: R² improved from -0.25 to 0.77.

XGBoost still narrowly outperforms this model (0.80 vs. 0.77 R²) on this task.

## 3. AI4I 2020 Failure Classification (XGBoost)

**Task:** binary machine-failure prediction and multiclass failure-mode classification (TWF, HDF, PWF, OSF, or no failure) from AI4I 2020 sensor telemetry.

**Performance (5-fold cross-validation):**
| Metric | Mean | Std |
|---|---|---|
| Accuracy | 0.921 | 0.006 |
| Precision | 0.295 | 0.016 |
| Recall | 0.956 | 0.009 |
| F1 | 0.451 | 0.020 |
| ROC-AUC | 0.976 | 0.004 |
| PR-AUC | 0.758 | 0.047 |

**Why high recall, low precision:** `scale_pos_weight` was deliberately tuned to prioritize recall (95.6%) over precision (29.5%) — in a maintenance context, a missed failure (false negative) is materially more costly than an unnecessary inspection (false positive). This is a deliberate, defensible tradeoff, not an unaddressed class-imbalance artifact.

## 4. Anomaly Detection: Isolation Forest vs. Autoencoder (AI4I 2020)

Both models flag the same fixed proportion of the dataset (top 5% by anomaly score) as anomalous, trained only on normal (non-failure) rows.

| Metric | Isolation Forest | Autoencoder |
|---|---|---|
| Precision | 0.200 | 0.128 |
| Recall | 0.357 | 0.209 |
| F1 | 0.257 | 0.159 |

**Selection:** Isolation Forest is the production choice — it outperforms the autoencoder on every metric here, at lower implementation and training complexity.

**Reproducibility note:** the autoencoder was initially unseeded, producing meaningfully different results on every run (precision ranged 12.8%–23.3% across identical-code runs). `torch.manual_seed()` was added and verified sufficient here (unlike the LSTM RUL and forecasting models — see Decision Log) to produce bit-identical results across repeated runs.

## 5. CMAPSS Sensor Forecasting LSTM (FD001)

**Task:** forecast 15 real sensor readings 2 cycles ahead from a 5-cycle window of engineered features.

**Architecture:** single-layer LSTM, 32 hidden units, input size 107 (matching the RUL feature set, minus the RUL target itself), output width `15 sensors × 2 horizon steps = 30`. Adam optimizer, learning rate 0.01, 30 epochs. Seeded identically to the RUL LSTM (`torch.manual_seed` + `use_deterministic_algorithms`); verified bit-identical output across repeated runs.

**Performance (official FD001 test set, 20,031 evaluation sequences), on [0,1]-scaled sensor values:**

| Metric | Value |
|---|---|
| Overall RMSE | 0.108 |
| Overall MAE | 0.083 |

Per-sensor RMSE ranges from 0.055 (`sensor_measurement_14`, easiest to forecast) to 0.172 (`sensor_measurement_6`, hardest to forecast) — see `ml/artifacts/forecasting/metrics.json` for the full per-sensor breakdown.

**Debugging note — target leakage:** an earlier version of this model included `rul` (the RUL target used elsewhere in this project) as one of its own input features, alongside excluding only `unit_number` and `time_in_cycles`. This meant the model was trained with access to information it would never realistically have at real inference time. Fixed by excluding `rul` from the feature set; input size correctly dropped from 108 to 107.

**Debugging note — API contract mismatch:** the backend forecasting service originally required callers to submit fully pre-engineered feature rows (~107 columns including rolling statistics) rather than raw sensor readings, which no real caller would have. Fixed by having the service reconstruct the same rolling/trend/baseline-diff features internally from raw sensor history, matching how the regression service already worked.
